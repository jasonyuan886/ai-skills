# 发布结果核验方法论

## 一、铁律：published_hint 不是判据

发布脚本判断成功的方式通常是点完发布按钮后抓一次 UI 界面文字，看有没有 "sharing"/"published"：
```python
published_hint = "sharing" in xml.lower() or "published" in xml.lower()
```
界面稍变或抓取时机差几秒就检测不到。**假阴性（实际发了但报没发）非常常见**，据此重发会造成重复发布。

实证：`oddly_satisfying_seal` 的 YouTube 视频 2026-09-21 06:27:15 已经在频道上线，而系统里 youtube 平台**一条记录都没有**。

所以核验必须用**外部可观测的事实**，不能用脚本自述。

## 二、核验优先级（从便宜到贵）

### 第 1 优先：站外免登录公开信源 ← 能用这个就别往下走

**YouTube 是最容易的**，频道 RSS 完全公开、无需登录、无风控：
```bash
# 1. 从频道页取 channel_id
CID=$(curl -s -A "Mozilla/5.0" "https://www.youtube.com/@<handle>" \
      | grep -o 'channel_id=[A-Za-z0-9_-]\{24\}' | head -1 | cut -d= -f2)

# 2. 读最近上传列表（标题+发布时间）
curl -s "https://www.youtube.com/feeds/videos.xml?channel_id=$CID"
```
拿内容包的 `title` 去比对即可定论。

**判断"不存在"要先确认覆盖范围**：feed 只返回最近 ~15 条。要确认 feed 的时间跨度是否覆盖了推送时刻——实战里 feed 连续覆盖 9/08–9/21（含推送后半小时的两条上传），所以"没有这个标题"是确凿的不存在，不是被截断。**这一步不做，结论就不成立。**

这个办法 2026-09-22 一次性定论了两条记录，**完全没开云手机、零成本**：
- `knife_prep_to_seal` / youtube → 推送于 13:22:49 UTC，feed 里无此标题 → **确认未发布**
- `oddly_satisfying_seal` / youtube → 标题在 feed 里（06:27:15 上线）→ **确认已发布**

**其他三个平台实测都不行**（2026-09-21）：
| 平台 | 结果 |
|---|---|
| Instagram | HTTP 200 但页面含登录/验证墙 |
| TikTok | HTTP 200 但含登录/验证墙 |
| Facebook | HTTP 302 直接跳登录 |

所以 IG/TikTok/FB 只能走第 2 优先。

### 第 2 优先：云手机开 App 看自家主页

第三方远程控制后台打不开时，用 ADB 自己做：深度链接直达主页 → 截图 + 抓界面文字。具体时序和各平台深度链接可用性见 [[cloud-phone-adb-publishing]] 第三节。

**要限定操作边界**：只允许"打开页面 + 截图 + 读界面层级"，兜底点击只允许点导航标签白名单（Profile/Me/You），绝不接受任意坐标——这样不可能误触发布。

实战拿到的证据示例：
- Instagram 主页：`18 posts / 0 followers / 10 following` + 网格缩略图
- TikTok 主页：`@handle 36关注/13粉丝/34赞` + 各视频播放量（`150 / 122 / 505 / 100 / 264`）
- **异常信号**：TikTok 网格左上角第一格显示 `0 播放`且缩略图空白，而该条推送已过去 17 小时——正常发布的视频不该是这个状态，值得单独深究

### 第 3 优先：人工进后台翻页

前两步都不行才用。注意远程控制后台可能加载不出来（WebRTC/拦截器/网络），别把它当唯一路径。

## 三、改判要留证据

核验出结果后用 record 固化，**消息里写清判据来源**，不要只写结论：
```bash
python3 content_queue.py record <file>.json youtube 1 \
  "公开频道核查：频道feed连续覆盖9/08-9/21，无此标题，确认未发布"

python3 content_queue.py record <file>.json youtube 0 \
  "公开频道核查：2026-09-21T06:27:15已上线，确认已发布"
```
退出码约定：`0`=verified（确实发了，封终态防重发）、`1`=failed（确实没发，转可重试）、`2`=pushed。

**顺序很重要**：如果这条内容接下来要归档/移出队列，**先 record 再归档**。否则将来内容被恢复时，系统会以为没发而重发一遍。

## 四、别把"看不到"当成"没发"

三条实战教训：
- **主屏没有 App 图标 ≠ 没装**。用 `pm list packages -3` 查，App 可能在应用抽屉里（实测四个社媒 App 都装着，主屏一个都看不到）
- **App 打不开 ≠ 没登录**。Facebook 被 Google Play 更新弹窗整个挡住，但背景能看到账号头像和信息流，其实是登录着的
- **报错信息要按字面读**。YouTube 报 `you should run glogin to login first` 指的是 ADB 认证没过，不是社媒账号没登录

## 五、核验闭环建议

自动发布跑完之后，**不要只看脚本返回码就算完**：
1. 看 `publish_status.json` 记录了什么
2. YouTube 走公开 RSS 核验（零成本，必做）
3. IG/TikTok 开一次云手机抓主页图确认（一次开机把几个平台一起看完，看完立刻关机）
4. 有出入就 record 改判，把事实固化下来

这套闭环的价值在于：它让"系统以为的状态"和"平台上的真实状态"定期对齐，避免误差累积成重复发布或长期漏发。
